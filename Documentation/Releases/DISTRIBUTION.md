# Distribution

How Qeetrix for iOS reaches an app, and why. Versions and what they promise are in `RELEASE_POLICY.md`.

## Decision

**A source-based Swift package, from the private Git repository `github.com/qeetgroup/qeetrix-ios`,
with SemVer tags.** No binary framework, no CocoaPods, no Carthage, no package registry.

Why:

- **It is how the package is built.** One library product, `Qeetrix`, with fonts, licences and
  metadata as SwiftPM resources (ADR 0001). Xcode and SwiftPM consume it with no extra tooling.
- **Nothing calls for a binary.** A binary XCFramework would need library evolution, module stability,
  signing and a second build pipeline. It would hide sources that Qeet Group already owns, and it would
  make debugging harder. There is no licensing or commercial requirement for one; revisit this if a
  consumer outside Qeet Group ever needs the library without its sources.
- **Access is the repository's.** The repository is private, so an app's developers and CI need read
  access to it. No separate distribution channel or credential is introduced.

## Installing

Once a version is tagged — none is yet — an app adds the package by URL and version.

**Xcode:** File › Add Package Dependencies…, enter `https://github.com/qeetgroup/qeetrix-ios.git`, choose
the version rule below, and add the `Qeetrix` library to the app target.

**A package manifest:**

```swift
dependencies: [
    // Before 1.0, a minor version may break source (RELEASE_POLICY.md): take patches only.
    .package(url: "https://github.com/qeetgroup/qeetrix-ios.git", .upToNextMinor(from: "0.1.0"))
],
targets: [
    .target(name: "App", dependencies: [.product(name: "Qeetrix", package: "qeetrix-ios")])
]
```

Don't use `from: "0.1.0"`: before 1.0 it accepts every 0.x version, including ones that break source.
To try a release candidate, pin it exactly: `exact: "0.1.0-rc.1"`. SwiftPM never chooses a pre-release
unless asked.

Until the first tag exists, the only way in is a branch or revision (`branch: "main"`, `revision:`),
which is for evaluation, not for shipping.

## What an app gets

- **The `Qeetrix` module**, with no dependencies of its own. The test-only packages (snapshot testing
  and its dependencies) are never resolved by an app. `Scripts/consumer-check.sh` checks this: the
  consumer's `Package.resolved` lists Qeetrix alone.
- **A resource bundle** (`Qeetrix_Qeetrix.bundle`, about 1.5 MB), with:
  - the two fonts and their OFL licences (`Fonts/`);
  - the icon artwork's notice (`Licenses/`);
  - the token provenance (`Metadata/`);
  - the built-in strings (`en.lproj`).
- **Nothing to run at build time.** Tokens and icons are generated and committed. No Node.js, no web
  packages, no sibling repositories, no generator. `Tools/` and `Upstream/` exist only to regenerate.
- **No network access, data collection or privacy manifest** (`LICENSE_COMPLIANCE.md` and
  `Documentation/Quality/SECURITY_PRIVACY_REVIEW.md`).

## Requirements

| | Supported | Verified |
|:--|:--|:--|
| Platforms | iOS and iPadOS 17 or later | iOS 27.1 simulator (iPhone). iOS 17 and iPad: not yet (`COMPATIBILITY_MATRIX.md`) |
| Toolchain | Xcode with Swift 6 (the manifest is `swift-tools-version: 6.0`) | Xcode 27.1, Swift 6.4 |
| Language mode | Swift 6; an app in Swift 5 mode can depend on it | Swift 6 consumer only |

The manifest also names macOS 14. That lets `swift build` and `swift test` run on a Mac during
development; macOS isn't a supported platform for apps.

## Security considerations

- Every upstream input is pinned by hash (`Upstream/upstream.lock.json`), and CI fails on any change.
- The library has no dependencies to audit at run time. `Documentation/Releases/qeetrix-ios-0.1.0-rc.1.cdx.json`
  is the candidate's bill of materials, generated by `Scripts/sbom.sh`.
- Tags are the release: a published tag must never be moved or deleted (`ROLLBACK_PROCEDURE.md`). Signed
  tags are recommended when the owner creates one.

## Known limitations

- No version has been tagged; installation by version has been tested only against a throwaway
  repository (`CONSUMER_INTEGRATION.md`).
- Access depends on GitHub permissions to a private repository; CI systems that build apps need a
  read-only credential for it.
